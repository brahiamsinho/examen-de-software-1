# Design: Cycle 2 — Multi-Tenant Identity (Users, Organizations, Memberships)

> Size note: this document deliberately exceeds the default 800-word design budget. The file/module
> architecture section was explicitly requested as the most complete section of this artifact.

## Technical Approach

Two new Django apps, `backend/apps/users/` and `backend/apps/organizations/` (split per Django's
one-app-per-domain convention), carrying the project's **first** `models.py` files and **first**
migrations. They follow Cycle 1's layering discipline without inheriting its DB-free constraint:

```
HTTP (api.py, thin)  →  permissions.py (authorization)  →  services.py (invariants, transactions)
                                                             ↓
                                                        models.py (ORM + scoping)
```

- `api.py` routers contain **no business logic**: parse schema → resolve membership → check role →
  call one service function → serialize. Every non-trivial rule (last-owner, duplicate membership,
  email lookup, creator-becomes-OWNER) lives in `services.py` and is unit-tested without HTTP, so a
  later Channels consumer or management command can call it directly (proposal D2/D4 seam).
- Tenant scoping is explicit by construction (D4): `TenantScopedModel` + a manager whose only
  public entry points are `for_organization(org)` and the greppable `.unscoped()`.
- Authentication is one seam only: Ninja's `django_auth` (D2). No endpoint reads `request.session`
  for authorization (D3 — tenant key is always a path segment).

Specs implemented: `user-authentication`, `organization-tenancy`, `organization-membership`,
`tenant-isolation`.

## Design Decisions

Continuing the proposal's D1–D7.

### DD1 — `TenantScopedModel`: raising default manager + instance-aware escape

**Choice.**

```python
class TenantScopedQuerySet(models.QuerySet):
    def for_organization(self, organization):
        return self.filter(organization=organization)


class TenantScopedManager(models.Manager.from_queryset(TenantScopedQuerySet)):
    def get_queryset(self):
        # Reverse related access (organization.memberships) is scoped by construction:
        # the related manager sets `instance`, so it is allowed through.
        if getattr(self, "instance", None) is not None:
            return super().get_queryset()
        raise TenantScopeViolation(
            f"{self.model.__name__} is tenant-scoped: use .for_organization(org) or .unscoped()."
        )

    def for_organization(self, organization):
        return self.unscoped().filter(organization=organization)

    def unscoped(self):
        return super().get_queryset()


class TenantScopedModel(models.Model):
    organization = models.ForeignKey(
        "organizations.Organization", on_delete=models.CASCADE,
        related_name="%(class)ss", null=False,
    )
    objects = TenantScopedManager()
    all_objects = models.Manager()

    class Meta:
        abstract = True
        base_manager_name = "all_objects"
```

**Alternatives considered.** (a) `get_queryset()` filtering from a thread-local "current org"
(rejected in proposal D4 — invisible tenancy, dies in async/Channels). (b) A non-raising manager
that only *offers* `for_organization` (rejected: `Membership.objects.all()` would still silently
return every tenant's rows, so the isolation test could not fail). (c) Raising unconditionally
(rejected: breaks `organization.memberships.all()`, `Model.refresh_from_db`, and the delete
collector).

**Rationale.** `base_manager_name = "all_objects"` keeps Django's internals — cascade collection,
FK descriptors, `refresh_from_db` — on a plain manager, so the guard never breaks the ORM. The
`instance` check permits reverse access that is *already* org-bound while still making
`Membership.objects.all()` a hard, testable failure. `.unscoped()` is one greppable token.

**Known consequence.** `django.contrib.admin` and `dumpdata` use `_default_manager` and would
raise for tenant-scoped models. Admin registration is explicitly not a deliverable; if added, use
`all_objects`. This is recorded as tech debt, not worked around.

### DD2 — Cross-origin session + CSRF settings (resolved; the spec deferred this here)

**Choice** — appended to `backend/config/settings.py`, all env-driven:

```python
# --- Session / CSRF (cross-origin cookie session with the Next.js frontend) ---
CSRF_TRUSTED_ORIGINS = env.list("CSRF_TRUSTED_ORIGINS", default=[])
CORS_ALLOW_CREDENTIALS = env.bool("CORS_ALLOW_CREDENTIALS", default=True)

SESSION_COOKIE_SAMESITE = env("SESSION_COOKIE_SAMESITE", default="Lax")
CSRF_COOKIE_SAMESITE = env("CSRF_COOKIE_SAMESITE", default="Lax")
SESSION_COOKIE_SECURE = env.bool("SESSION_COOKIE_SECURE", default=not DEBUG)
CSRF_COOKIE_SECURE = env.bool("CSRF_COOKIE_SECURE", default=not DEBUG)

SESSION_COOKIE_HTTPONLY = True   # JS never needs the session cookie
CSRF_COOKIE_HTTPONLY = False     # the frontend MUST read csrftoken to echo it back
```

Deployment matrix, documented in `.env.example`:

| Environment | Frontend origin | `*_SAMESITE` | `*_SECURE` | Note |
|---|---|---|---|---|
| Local dev | `http://localhost:3000` → `:8000` | `Lax` | `False` | Different ports are still *same-site*, so `Lax` works and no HTTPS is needed. |
| Deployed, different domains | `app.example.com` → `api.example.com` | `None` | `True` | Browsers reject `SameSite=None` without `Secure`; both flip together. |

**Alternatives considered.** Hardcoding `SameSite=None; Secure=True` everywhere (rejected: breaks
plain-HTTP local dev, and this settings file's stated convention is that nothing is hardcoded).
Proxying the API under the frontend origin to make cookies same-origin (rejected: it hides the
CORS problem behind infrastructure the exam deliverable does not own, and Docker Compose already
exposes two ports).

**CSRF-token acquisition endpoint** (the piece the spec explicitly deferred): `GET /api/auth/csrf`,
anonymous, calls `django.middleware.csrf.get_token(request)` — which sets the `csrftoken` cookie —
and returns `{"csrf_token": "<token>"}` in the body as well, so a non-browser client (Flutter) can
use the double-submit header without parsing `Set-Cookie`. The frontend calls it once before its
first unsafe request and thereafter sends `X-CSRFToken`.

`NinjaAPI(csrf=True)` enforces the check API-wide; only unsafe methods are affected, so `/health`
and every `GET` are unchanged. Anonymous `POST /auth/register` and `POST /auth/login` are
CSRF-protected too — this is the reason the acquisition endpoint has to exist.

### DD3 — Service-layer signatures (invariants live here, not in views)

```python
# apps/users/services.py — keyword-only, HTTP-agnostic, raising apps/users/errors.py exceptions
def register_user(*, email: str, password: str, full_name: str = "") -> User: ...
def authenticate_user(*, email: str, password: str) -> User: ...           # raises InvalidCredentialsError

# apps/organizations/services.py — same conventions, raising apps/organizations/errors.py exceptions
def create_organization(*, owner: User, name: str, slug: str,
                        plan: str = Plan.STARTER) -> Organization: ...      # @transaction.atomic
def rename_organization(*, organization: Organization, name: str) -> Organization: ...
def delete_organization(*, organization: Organization) -> None: ...         # hard delete, cascades
def list_user_organizations(*, user: User) -> QuerySet[Organization]: ...

def add_member(*, organization: Organization, email: str, role: str) -> Membership: ...
def change_member_role(*, organization: Organization, target_user_id: UUID,
                       new_role: str) -> Membership: ...                    # @transaction.atomic
def remove_member(*, organization: Organization, target_user_id: UUID) -> None: ...  # @transaction.atomic
def list_memberships(*, organization: Organization) -> QuerySet[Membership]: ...

def _assert_not_last_owner(*, organization: Organization, membership: Membership) -> None: ...
```

`_assert_not_last_owner` is the single implementation behind both the demote and the remove path:

```python
if membership.role != Role.OWNER:
    return
remaining = (
    Membership.objects.for_organization(organization)
    .filter(role=Role.OWNER)
    .exclude(pk=membership.pk)
    .select_for_update()      # inside the caller's atomic block
    .count()
)
if remaining == 0:
    raise LastOwnerError("An organization must always have at least one OWNER.")
```

**Rationale.** One helper, two call sites — the invariant cannot drift between demotion and
removal. `select_for_update()` inside the caller's transaction closes the race where two concurrent
demotions each see the other owner still present and both succeed. Keyword-only arguments make call
sites self-documenting and prevent `(org, user)` / `(user, org)` transpositions.

`create_organization` creates the `Organization` and the `OWNER` `Membership` in one
`transaction.atomic()` block, satisfying "in the same transaction" from `organization-tenancy`.

### DD4 — `resolve_membership()` as an explicit call, not Ninja auth or middleware

**Choice.** Django Ninja has no FastAPI-style dependency injection. The resolver is a plain function
invoked as the first statement of every tenant-scoped handler:

```python
# apps/organizations/permissions.py
def resolve_membership(request: HttpRequest, org_slug: str) -> Membership:
    """404 for an unknown slug AND for a non-member — indistinguishable by design."""
    try:
        return (
            Membership.objects.unscoped()
            .select_related("organization", "user")
            .get(organization__slug=org_slug, user=request.user)
        )
    except Membership.DoesNotExist:
        raise Http404("Organization not found")


def require_role(membership: Membership, *allowed: Role) -> None:
    if membership.role not in allowed:
        raise RoleNotAllowedError(...)   # → 403
```

**Alternatives considered.** A custom Ninja auth class resolving the org (rejected: Ninja auth
callables receive only `request`; reading the slug from `request.resolver_match.kwargs` is fragile
and untestable in isolation). Middleware (rejected by proposal D4). A decorator (rejected as the
*primary* mechanism: it hides the `Membership` the handler then needs, forcing a `request` stash
that is the thread-local smell again).

**Rationale.** A single `.get()` against the `Membership` table answers "does this org exist *for
this caller*" in one query, which is exactly why unknown-slug and non-member collapse to the same
404 without any branch that could accidentally leak existence. The `.unscoped()` call is correct
and intentional here: the resolver is the one place that legitimately looks across organizations,
and its ugliness is the signal D4 asked for.

### DD5 — UUID primary keys for `User` and `Organization`

**Choice.** `User.id` and `Organization.id` are `UUIDField(primary_key=True, default=uuid4,
editable=False)`. `Membership` keeps the project's `BigAutoField` default and is never exposed in a
URL or payload (member routes are keyed by `user_id`).

**Alternatives considered.** Sequential integers everywhere (rejected by D3: enumerable, leaks
tenant and user counts). UUID on `Membership` too (rejected: no external identity, so it would be
index cost with no benefit).

### DD6 — Error taxonomy mapped centrally, not per-handler

Services raise `errors.py` exceptions; `api.register_exception_handlers(api)` maps them once:

| Exception | Status | `code` |
|---|---|---|
| `DuplicateEmailError` | 409 | `duplicate_email` |
| `PasswordPolicyError` | 400 | `password_invalid` |
| `InvalidCredentialsError` | 401 | `invalid_credentials` |
| `DuplicateSlugError` | 409 | `duplicate_slug` |
| `UserNotFoundError` | 404 | `user_not_found` |
| `DuplicateMembershipError` | 409 | `duplicate_membership` |
| `LastOwnerError` | 409 | `last_owner` |
| `RoleNotAllowedError` | 403 | `forbidden` |
| `Http404` (non-member / unknown slug) | 404 | `not_found` |
| Ninja schema validation | 422 | *(Ninja default)* |

`UserNotFoundError` returning 404 does not conflict with the tenant-isolation contract: only an
authenticated `OWNER` of the org can reach it, and the subject is an email in the request body, not
the tenant.

### DD7 — Case-insensitive email uniqueness enforced twice

`UserManager.normalize_email` lowercases the whole address (not just the domain, which is Django's
default) before save, **and** `Meta.constraints` carries
`UniqueConstraint(Lower("email"), name="users_user_email_ci_unique")`. Application-level
normalization gives a clean 409 with a readable message; the Postgres functional index makes the
guarantee true even for a writer that bypasses the manager. Rejected: `CITextField` (requires the
`citext` extension and a migration privilege the exam environment may not have).

### Schemas — `schemas.py`

```python
class RegisterIn(Schema):   email: EmailStr; password: str; full_name: str = ""
class LoginIn(Schema):      email: EmailStr; password: str
class UserOut(Schema):      id: UUID; email: str; full_name: str
class CsrfOut(Schema):      csrf_token: str

class OrganizationIn(Schema):      name: str; slug: str; plan: Plan = Plan.STARTER
class OrganizationPatchIn(Schema): name: str
class OrganizationOut(Schema):     id: UUID; name: str; slug: str; plan: str; my_role: str | None

class MemberAddIn(Schema):   email: EmailStr; role: Literal["EDITOR", "VIEWER"]
class RoleChangeIn(Schema):  role: Role
class MembershipOut(Schema): user_id: UUID; email: str; full_name: str; role: str; created_at: datetime

class ErrorOut(Schema):      detail: str; code: str
```

`MemberAddIn.role` is deliberately narrower than `RoleChangeIn.role`: the
`organization-membership` spec allows adding only `EDITOR` or `VIEWER`, while a role *change* may
promote to `OWNER`. The narrowing is enforced by the schema type, so it is a 422 at the edge rather
than a service branch.

## Data Flow

```
Browser (Next.js, other origin)
   │  1. GET /api/auth/csrf ───────────────► sets csrftoken cookie + body token
   │  2. POST /api/auth/login (X-CSRFToken) ► services.authenticate_user ──► django.contrib.auth.login
   │                                                                          └─► sessionid cookie
   │  3. GET /api/orgs/{slug}/members (cookies)
   ▼
config/api.py  ──► django_auth (session)  ──► apps/organizations/api.py handler
                                                 │
                                                 ├─► permissions.resolve_membership(request, org_slug)
                                                 │        └─ Membership.objects.unscoped().get(...) → 404 or Membership
                                                 ├─► permissions.require_role(membership, Role.OWNER)   → 403
                                                 └─► services.<operation>(organization=membership.organization, ...)
                                                          └─► Membership.objects.for_organization(org)  [scoped]
                                                                   │
                                                              errors.py ──► exception handler ──► ErrorOut
```

The only cross-organization query in the whole app is inside `resolve_membership`, and it is
written with the explicit `.unscoped()` token so a `rg "\.unscoped\(\)"` audit is a complete list.

## Testing Strategy

Strict TDD Mode is enabled: every work unit writes the RED test first. This is the project's first
DB-backed suite — the first work unit that touches the database MUST land the `django_db` setup
(marker usage, `conftest.py` fixtures, and the documented Postgres prerequisite) rather than
deferring it.

| Layer | What to test | Approach |
|---|---|---|
| Model | Field shapes, constraints, cascades, manager behaviour | `@pytest.mark.django_db`, direct ORM assertions; `IntegrityError` under `pytest.raises` for constraints |
| Isolation contract | Every concrete `TenantScopedModel` subclass is scoped-only | Reflection over `TenantScopedModel.__subclasses__()` + `apps.get_models()`; asserts a non-null `organization` FK and a raising default manager. Fails automatically when a future cycle adds a subclass |
| Service | Every invariant (last owner, duplicate email/slug/membership, unregistered email, creator-becomes-OWNER, self-removal) | `@pytest.mark.django_db`, calling `services.*` directly — **no HTTP client**, so later Channels/management-command callers are covered by the same tests |
| Permission | 404-not-403, unknown slug, role gating | Call `resolve_membership` / `require_role` with a `RequestFactory` request |
| API (integration) | Status codes, response bodies, session lifecycle | Django test `Client` against the mounted Ninja routes |
| Cross-origin / CSRF | Token acquisition, rejection without token, acceptance with `X-CSRFToken`, `SameSite=None ⇒ Secure` | `Client(enforce_csrf_checks=True)` plus `override_settings` for the deployed matrix — **the cross-origin flow, not just same-origin** (the proposal's High risk) |

`factories.py` provides plain builders (no new dependency, matching
`apps/uml_modeling/tests/factories.py`):

- `make_user(*, email=None, password="…", full_name="")` — unique email via a module counter.
- `make_organization(*, owner=None, name=None, slug=None, plan=Plan.STARTER)` — creates the owner
  and its `OWNER` `Membership`; returns the `Organization`.
- `make_membership(*, organization, user=None, role=Role.EDITOR)`.
- `make_org_with_roles()` — returns `(organization, owner, editor, viewer, outsider)`, the fixture
  shape most authorization tests need.

`apps/uml_modeling/` tests stay DB-free and untouched, so the "which tests need Postgres" split
remains visible per file.

## Migration / Rollout

**Confirmed: this is genuinely the project's first migration.** No `migrations/` package exists
anywhere under `backend/`, and `apps/uml_modeling/` has no `models.py` at all — so nothing depends
on `auth.User` and the swap costs nothing.

Ordering, which matters and must not be reordered:

1. Create `backend/apps/users/__init__.py` and `apps.py` with `label = "users"`, and
   `backend/apps/organizations/__init__.py` and `apps.py` with `label = "organizations"`.
2. In `settings.py`, add `"apps.users"` and `"apps.organizations"` to `INSTALLED_APPS` **and** set
   `AUTH_USER_MODEL = "users.User"` — both before any `makemigrations` run.
3. Write `apps/users/models.py` (`User`) then `apps/organizations/models.py` (`Organization`,
   `TenantScopedModel`, `Membership`), since `Membership.user` is a FK to `AUTH_USER_MODEL`.
4. `python manage.py makemigrations users organizations` → one `0001_initial.py` per app; review
   both by hand for the `Lower("email")` constraint (`users`), the `(user, organization)` unique
   constraint and `swappable_dependency` handling (`organizations`).
5. `python manage.py migrate` against an empty database.

Steps 1–2 must be one commit with step 3–4; a `makemigrations` run before `AUTH_USER_MODEL` is set
would generate migrations against `auth.User` and poison the graph.

**Test database.** `pytest-django` builds a test database from the `POSTGRES_*` env vars, so a
reachable `db` service becomes a hard prerequisite for `cd backend && pytest`. Document this in
`docs/ai/CURRENT_STATE.md`.

**Rollback** follows the proposal's staged plan unchanged: `migrate organizations zero` then
`migrate users zero` before real data exists; a pre-`migrate` `pg_dump` is mandatory before the
first deployment; unmounting the routers in `config/api.py` is always a safe partial rollback that
leaves the schema intact.

## Open Questions

- [ ] The proposal's question round (auto-created personal organization, hard vs. soft org delete,
      viewer presence visibility, frontend timing) went unanswered. This design assumes the stated
      defaults, which the specs then froze: **no** auto-created organization, **hard** delete,
      viewer fully visible. If the answers change, `organization-tenancy` and
      `user-authentication` change with them.
- [ ] `django.contrib.admin` is in `INSTALLED_APPS` but registering `Membership` would hit the
      raising default manager (DD1). Left unregistered this cycle; if admin access is needed for
      the demo it must use `all_objects`.
- [ ] `Organization.slug` is client-supplied. This design validates its format via `SlugField` and
      rejects duplicates with 409, but does not auto-derive a slug from `name` or auto-deduplicate.
